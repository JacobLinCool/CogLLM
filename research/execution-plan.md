規劃基準日為 2026 年 11 月 20 日。**研究的執行由主 agent 負責到底。PI 監督進度、決定實驗設計，並解讀結果。** 本文件記錄分工、交付、驗收、時間和資源。研究問題及實驗方法見[訓練方案](training-protocol.md)，公式與模型介面見[數學規格](mathematical-formulation.md)。

研究只使用既有的人類觀測與已發表的實驗效應。驗證同一個 Qwen3.5-2B 能否一次因果 forward 重現反應的分布和條件差，並在資料有對應標註時驗證反應位置與所指原文區段。模型接受正文及選填背景，預設空背景對應事先定義的參考讀者群。已登錄 46 篇實證文獻，完成三套資料的對齊、個別基線、指涉效應監督與外部診斷，以及三任務共享訓練的逐次與效應對照。後續加入可定位的局部端點並擴充留出驗證，區分逐次反應、跨條件效應及發生位置。 [文獻及資料](reading-evidence.md) · [首輪共享結果](joint-first-run.md) · [聯合效應結果](joint-effects-run.md)

資料與模型優先取自 Hugging Face 公開儲存庫，個別資料依作者發布位置取得。正式訓練使用 **Google Colab 的 NVIDIA L4**，本機負責資料準備、來源重算與輕量程式測試。 [來源查核](reading-evidence.md#hugging-face-來源查核) · [L4 執行與驗收](#colab-l4-的執行與驗收)

## 完成條件

**CogLLM 模型。** 用同一個封存的 Qwen3.5-2B checkpoint，對每篇文章及指定背景做一次因果前向，輸出對得回原文的 token 和句級反應估計。正文是唯一必填輸入，背景欄位限於能用既有資料驗證的讀者群或知識條件。正式評估前固定核心觀測、分割、統計量與容許差。在留出材料逐項比較真人反應分布、條件效應方向及幅度。疑問出現、指向及解除各依對應標註的粒度驗收，有配對的軌跡才支持同一疑問的更新主張。精度不足及不可檢驗的效應保留在結果表。 [真人效度判定](mathematical-formulation.md#真人效度) · [逐位置讀出](mathematical-formulation.md#3-平行讀出反應位置與強度)

**論文和說明文。** 在連續解說的正文中驗證讀者在哪裡變得較難處理、強度如何、讀完有何整體反應。把解說順序、句子構成和銜接提示列入主要操弄。先在相同內容的不同寫法比較模型與真人的改變，再用已驗收的反應訊號做改寫比較。局部定位和篇後理解各依真人的實際觀測粒度驗收。 [論文解說反應與首批對照](expository-reading-plan.md)

**Gradio 文本分析工具。** 作者或編輯可以貼上文章、執行分析，點選位置查看原文範圍、端點強度與量尺，並在可用時回查上文指向及後續證據區間。使用正式封存 checkpoint，畫面標示參考讀者群、驗證粒度和實驗性輸出。端到端驗收涵蓋從輸入到原文標記、空背景、Unicode 偏移，以及替換後文時共有前綴的結果一致性。 [首版操作與結果畫面](app-concept.md)

## 分工與 PI 的決策點

| 角色 | 工作與交付 |
| --- | --- |
| 主 agent | 維護計畫與進度、分派子 agent、整合產出、裁決來源查核歧見、追蹤缺資料的效應。負責程式、資料前處理、訓練、測試、效應重算、資源監控、可重現性與結果報告。實驗設計部分由 agent 備妥候選方案、材料、估計式、成本和各方案會如何改變解讀。 |
| 子 agent | 依工作包獨立核對文獻、標註觀測、檢查資料版本與分母、實作和複查程式與分析。每個工作包有一名負責 agent、一個交付位置和一組驗收條件。主 agent 對最後整合結果負責。 |
| PI | 監督研究方向與進度。確定主要假說、優先評估的讀者群與既有測量端點、效應容忍差和模型實驗設計，並解讀模型與文獻結果。收到的是已附證據與取捨的決策摘要。 |

文獻閱讀、效應拆解、標註和裁決都由 agent 執行，包含找原文頁碼、重算數字、訂標註規則，以及編碼既有的自由回報。工作量提高時由主 agent 增派子 agent 並驗收。Agent 編碼保留原始回報及改碼依據，證據與推論均可回查。

PI 的覆核集中在三個時間點。

1. **鎖定研究設計時。** Agent 提交已查證的效應清單、必驗端點、留出方式和判定容忍差，由 PI 決定研究優先順序及正式設計。獨立的文獻、資料和程式工作可以同步完成。
2. **固定留出驗證時。** Agent 提交可取得的材料與端點、證據涵蓋範圍、資料分割及分析規則。PI 覆核設計與主張範圍，agent 封存模型及評分規則後再跑留出評估。
3. **結果解讀時。** Agent 提交模型與真人的逐效應對照、定位誤差、失配及不確定性，並列出可區分競爭解釋的下一組對照。PI 決定科學解讀與後續方向。

## 文獻拆解與訊號選擇

主 agent 以實驗家族為工作單位分派。採用一篇論文內的多個觀察時，各有自己的觀測列。共用人類試次、刺激或重分析的文章記入同一家族。第一位 agent 從原文和資料抽取，第二位 agent 在看不到第一份抽取結果時核對入選效應。主 agent 回原始表格或資料裁決，記錄差異及理由。抽取一致性用來查核流程。

每筆觀察至少記錄下列資訊。

- **來源與設計。** 論文、實驗、頁碼或表圖、材料與試次家族、語言、讀者群、先備知識何時取得、任務、全文或前綴可見性，以及操弄的各條件。
- **觀測與統計。** 觀測端點、量尺、停點、所指原文、分母、排除條件、配對方式、效應方向、數值與估計不確定性。分開保留研究原報的數值及程式重算的數值。
- **可使用的訊號。** 原刺激加逐次反應可做直接監督。有原刺激與可對齊的彙總估計時可考慮效應損失。觀測粒度、材料或估計精度不足時記錄缺項。用途另記為開發訓練、開發診斷、整家族留出、待取得既有資料或僅供文獻背景，以及適用的讀出頭。 [弱監督方法先例](https://jmlr.org/papers/v11/mann10a.html)

資料清單另保存原始資料入口、取得狀態、釋出版、使用條件、雜湊和轉換程式。Agent 對既有自由回報的標註保留原讀者回報、編碼規則、角色、版本及對應區段。自編材料及合成資料可做模型內對照與工程測試。真人反應欄由既有研究的原始反應或出版數據填入。

第一批程式核對兩個已知結果。PLABA-EVAL 固定版本的 858 筆結構化讀者×句子中，452 筆至少勾選一項，406 筆明確回報沒有問題。華語續寫實驗的自由接寫條件按讀者等權重算，兩類動詞分別約為 77.7% 及 11.7%。此兩項用於驗證資料轉接和分母。 [PLABA-EVAL 盤點](reading-evidence.md#首輪訓練頭的資料盤點) · [華語原始試次](https://osf.io/download/8zk57/) · [華語論文 Fig. 1](https://doi.org/10.1371/journal.pone.0237012.g001)

### 資料及權重如何取得

- **模型。** 從官方 Hugging Face 儲存庫下載 `Qwen/Qwen3.5-2B` 的固定 revision `15852e8c16360a2fea060d615a32b45270f8a8fc`。訓練紀錄保存權重、設定和 tokenizer 的共同版本。 [官方固定版本](https://huggingface.co/Qwen/Qwen3.5-2B/tree/15852e8c16360a2fea060d615a32b45270f8a8fc)
- **資料。** 優先用內容完整、用途與使用條件可核查的 Hugging Face 公開版。Hub 版缺少原素材、逐次欄位或無法對應作者版時，在來源清單直接指定原作者的 GitHub 或 OSF。首輪的 PLABA-EVAL 與華語續寫目前由作者來源提供。 [首批來源與欄位](reading-evidence.md#hugging-face-來源查核)
- **版本與快取。** Hub 來源記錄 repo ID、commit SHA、config、split 和檔案；作者來源記錄版本、下載位置與檔案雜湊。先驗證對齊、列數和分割，再將版本固定的輸入放到 Colab 執行環境的本地磁碟。訓練時可依同一份清單取用，缺少關鍵欄位或版本不符的資料標記缺項，並繼續可用來源。

## 量測資源與更新排程

### Colab L4 的執行與驗收

1. **建立執行環境。** 使用專案專屬 Colab 工作階段，明確指定 `--gpu L4`。先驗證實際 GPU、可用 VRAM、CUDA、原生 BF16 和 PyTorch、Transformers、PEFT 版本。Transformers 5.17.0 列為候選，以固定 revision 的權重載入與讀出測試通過後鎖定實際套件版本。已核對本機 Colab CLI 0.7.4 接受 `L4` 參數。 [Transformers 對 Qwen3.5 的支援](https://github.com/huggingface/transformers/releases/tag/v5.2.0#qwen35-qwen35-moe) · [Colab 資源說明](https://research.google.com/colaboratory/faq.html)
2. **測試單次前向及特徵。** 以 PyTorch 取正文的語言路徑做一次因果 forward，先驗證 hidden states，再加入 attention 與 logit lens。核對後文替換、截短和 padding 一致性。Attention 先用可取得權重的實作作參考，其他實作按相同遮罩與特徵定義逐項比對。只抽選定層和位置的特徵，精度及分塊方式用 L4 實測決定。 [Qwen3.5 Transformers 實作](https://github.com/huggingface/transformers/blob/v5.17.0/src/transformers/models/qwen3_5/modeling_qwen3_5.py)
3. **跑訓練與量測。** 首輪凍結 Qwen，將特徵快取供讀出頭與效應損失比較。若啟用 LoRA，以可回傳梯度的語言路徑訓練。代表性短跑記錄有效 token/s、步耗時、CUDA 峰值記憶體和資料寫入時間。比較各特徵組合與模型容量時，保留相同的資料分割和端點。
4. **保存證據及釋放。** Agent 維護續跑 checkpoint，將權重、評估輸出、版本清單和執行紀錄下載並驗證，再釋放本次工作階段。Compute Units 以實際用量查詢記錄，並區分帳戶總用量與可歸於此實驗的用量。

### 本機已實測的最終層 forward

以本機 Apple M5 Pro、64 GiB 統一記憶體測試已下載的官方 Qwen3.5-2B BF16 revision `15852e8c16360a2fea060d615a32b45270f8a8fc`。環境是 MLX 0.32.2、MLX-LM 0.31.3。Batch size 1，以固定短文樣本 token 重複至各長度。使用 MLX 的文字路徑，先暖機一次，再各做五次 `encoder(tokens)` 並以 `mx.eval` 同步取回最終層表徵。峰值為 MLX 自身記錄的配置量。

| 序列長度 | 單次 forward 中位秒數 | 五次範圍（秒） | MLX 峰值（GiB） |
| --- | ---: | ---: | ---: |
| 256 | 0.0368 | 0.0366–0.0372 | 3.78 |
| 512 | 0.0667 | 0.0666–0.0667 | 3.93 |
| 1,024 | 0.1280 | 0.1278–0.1283 | 4.16 |
| 2,048 | 0.2584 | 0.2578–0.2588 | 4.22 |

表內時間是本機 MLX 的前向基準。排程以 L4 測得的完整資料處理、attention、logit lens 和訓練時間為準。重測時同時保留版本、硬體、tokenization、是否已暖機及同步方式。 [MLX 峰值記憶體](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_peak_memory.html) · [Qwen 模型架構](https://huggingface.co/Qwen/Qwen3.5-2B#model-overview)

### 下一輪要量的程式成本

1. **文獻工時。** 首批記錄每篇主抽取、獨立查核、裁決及等待取件的時間。目前以每篇 25–45 分鐘抽取、10–20 分鐘複查、5–15 分鐘對照裁決作規劃，46 篇合計約 31–61 agent 小時。拿到首批的實測後更新預算。
2. **完整特徵抽取。** 抽 30–60 篇有已知長度分布的材料，量測實際批次的 token/s、峰值、落盤大小，並分別測 hidden-only、加 attention、加 logits 的成本。依文章、背景、可見內容及模型版本去重，按各長度分桶用「輸入 token 數除以實測每秒處理量」估算運算時間，再加載入與寫入時間。以 30 萬唯一 token 為容量情境，保存 4 個 2,048 維 BF16 hidden layers 約需 4.58 GiB，另加索引與其餘特徵。Attention 和詞彙 logits 在每批縮減成指定特徵，快取精確使用的層與位置。
3. **讀出頭、效應訓練與驗證。** 記錄 CPU/GPU 時、批次大小、完整對比的條件數、字數與有效 token、峰值及重跑次數。凍結特徵可在架構一致的對照間共用，折內的標準化及參數估計按訓練分割重做。若啟用 LoRA，先在 L4 跑 20–50 個實際訓練步。以每輪 30 萬處理 token、2–3 輪、1–2 次訓練為規劃情境，總共 60–180 萬 token。若 L4 的實測訓練吞吐量落在每秒 50–300 token，約 0.6–10 GPU 小時，驗證、重啟和額外切分另計。正式批次與序列長度依 L4 的實測峰值設定。
4. **既有回報的編碼與核對。** 先選一批實際紀錄，量測文字對齊、類別編碼、獨立複查和裁決各自耗時。總工時以待編碼的既有回報數乘以實測每筆耗時，再加上需要逐筆裁決的案例。現成的結構化欄位以程式驗證分母與缺標即可開始，估計量不與人工編碼混算。
